# setInterval 与 setTimeout

## 概念框架

### Why — 为什么需要定时器

JavaScript 是单线程的，定时器是让代码"延后执行"或"周期执行"的唯一机制。没有它，所有代码只能同步顺序跑。

### What — 两者是什么

| | setTimeout | setInterval |
|---|---|---|
| 行为 | 延迟 N ms 后执行**一次** | 每隔 N ms 执行**一次**（直到清除） |
| 返回值 | timer ID | timer ID |
| 清除 | clearTimeout(id) | clearInterval(id) |

### How — 内部机制

定时器**不保证精确**。流程：

```
调用 setTimeout(fn, 1000)
  → 浏览器/Node 注册一个定时器
  → 1000ms 后把 fn 放入任务队列
  → 等当前调用栈清空后，事件循环取出 fn 执行
```

关键：**fn 不是在 1000ms 时执行，而是在 ≥1000ms 且主线程空闲时执行。**

## 核心区别：累积误差

实验中用 300ms 的阻塞模拟主线程繁忙，结果：

**setInterval** — 误差会**累积**：
```
tick=1  实际间隔=1004ms  误差=4ms
tick=2  实际间隔=2005ms  误差=5ms
tick=3  实际间隔=3021ms  误差=21ms
tick=4  实际间隔=4206ms  误差=206ms   ← 累积了前一次的阻塞
tick=5  实际间隔=5506ms  误差=506ms   ← 继续累积
```

原因：setInterval 按固定节奏往队列塞回调。如果前一次还没执行完，下一次的回调已经在队列里等着了。主线程一旦空闲，积压的回调会**连续执行**，节奏完全被打乱。

**递归 setTimeout** — 误差**不累积**：
```
tick=1  误差=4ms
tick=2  误差=4ms
tick=3  误差=4ms
tick=4  误差=5ms
tick=5  误差=5ms   ← 始终稳定
```

原因：每次回调执行**完毕后**才开始计算下一个 1000ms，所以前一次的阻塞不会影响后续间隔。

## 递归 setTimeout 模式

```js
function repeatedTask() {
  // 做一些事...
  setTimeout(repeatedTask, 1000); // 做完后才注册下一次
}
setTimeout(repeatedTask, 1000);
```

这是替代 setInterval 的常用模式，优势：
- 不会累积误差
- 不会出现多个回调积压在队列中
- 可以根据每次执行的结果动态调整下一次间隔

## 知识定位

### JS 代码的分类：同步 vs 异步

```
JavaScript 代码
├── 同步 — 立即执行，调用栈直接跑（如 console.log、变量赋值、函数调用）
└── 异步 — 延后执行，交给事件循环调度
      ├── 微任务 — Promise.then / catch / finally、MutationObserver、queueMicrotask
      │         优先级高，本轮同步跑完后立刻清空
      └── 宏任务 — setTimeout / setInterval、I/O 回调、UI 事件、setImmediate(Node)
                优先级低，下一轮事件循环才取
```

优先级：**同步 > 微任务 > 宏任务**

```js
console.log('1');                                // 同步，立即
setTimeout(() => console.log('2'), 0);           // 宏任务，注册后不等待
Promise.resolve().then(() => console.log('3'));  // 微任务，注册后不等待
console.log('4');                                // 同步，立即
// 输出：1 → 4 → 3 → 2
```

### 事件循环每一轮

```
1. 取一个宏任务执行
2. 清空所有微任务（一个接一个，直到队列空）
3. 渲染（如果需要）
4. 回到 1
```

定时器属于**宏任务（macrotask）**，每轮事件循环只取一个宏任务执行，之后清空所有微任务。

## 既然递归 setTimeout 能覆盖 setInterval，setInterval 存在的意义是什么

功能上 setTimeout 递归确实能替代 setInterval，但 setInterval 仍有存在价值：

**语义更清晰**
```js
// 意图一目了然——"每秒执行"
setInterval(() => updateClock(), 1000);

// 递归模式：意图被实现细节干扰
function tick() {
  updateClock();
  setTimeout(tick, 1000);
}
tick();
```
代码是写给人看的，setInterval 直接表达了"周期性"这个意图。

**最小延迟限制**

浏览器对嵌套超过 5 层的 setTimeout 会强制将延迟提升到至少 **4ms**（HTML 规范要求）。所以 `setTimeout(fn, 0)` 递归调用时，实际间隔不会低于 4ms。setInterval 不受此限制。

**性能开销**
- setInterval：注册一次，引擎内部维护一个周期定时器
- 递归 setTimeout：每次执行完都要重新注册，涉及宏任务入队/出队

高频率定时任务下这个差异是有意义的。

**历史原因**

setInterval 比 setTimeout 更早出现。早期 JS 主要用于网页简单交互（跑马灯、时钟），不需要考虑主线程阻塞问题，setInterval 够用了。后来的复杂场景才暴露出它的缺陷。

## 什么时候用哪个

| 场景 | 选择 | 原因 |
|---|---|---|
| 延迟执行一次（如 toast 3秒后消失） | setTimeout | 只需要一次 |
| 简单时钟/倒计时 | setInterval | 语义清晰，短期使用误差可忽略 |
| 固定节奏轮询（如每5秒检查状态） | 递归 setTimeout | 避免请求积压 |
| 回调执行时间可能超过间隔 | 递归 setTimeout | setInterval 会积压 |
| 需要动态调整间隔 | 递归 setTimeout | setInterval 不方便调整 |
| 动画帧 | requestAnimationFrame | 更准确、与屏幕刷新同步 |

## 网络请求的 Promise.then 到底经历了什么

"微任务优先级高"指的是**回调进入队列后**的优先级，跟请求本身耗时无关。

```
时间线：

0ms     fetch(url).then(res => console.log('拿到了'))

        JS 线程：调用 fetch()，告诉浏览器"帮我请求这个"，注册 .then 回调
        JS 线程：不等待，继续跑后续同步代码

        ===== 网络线程在后台跑，和 JS 线程无关 =====

5000ms  网络线程：收到响应数据，通知事件循环

        事件循环：把 .then 回调放入微任务队列
        当前宏任务执行完毕 → 清空微任务 → .then 回调执行
```

角色分工：

```
┌─────────────────────────────────────────┐
│  JS 线程（单线程）                        │
│  - 调用 fetch()，注册 .then 回调          │
│  - 继续跑同步代码                         │
│  - I/O 完成后执行 .then 回调              │
└──────────────┬──────────────────────────┘
               │ 发起请求 / 接收结果
┌──────────────▼──────────────────────────┐
│  浏览器底层（多线程）                      │
│  - 网络线程：真正的 HTTP 请求             │
│  - DNS 线程：域名解析                     │
│  - TCP 线程：建立连接                     │
│  ...这些和 JS 线程并行运行               │
└─────────────────────────────────────────┘
```

**JS 单线程 ≠ 整个浏览器单线程。** 耗时的 I/O 操作交给浏览器的其他线程，完成后通过事件循环通知 JS 线程处理回调。Node.js 同理，网络/文件 I/O 由 libuv 的线程池处理。

### 微任务的隐患：队列阻塞

微任务是同步清空的，如果微任务里又产生新的微任务，队列会一直涨：

| 微任务数量 | 执行耗时 | 宏任务被延迟 |
|---|---|---|
| 100 | ~0.1ms | 几乎无感 |
| 1,000 | ~0.3ms | 几乎无感 |
| 10,000 | ~4ms | 开始有感知 |
| 100,000 | ~30ms | 明显阻塞，页面卡顿 |

微任务队列不清空，后续的宏任务和渲染都无法执行。

## 费曼总结

JS 是单线程的。有同步代码，有异步代码。其中异步代码又分为微任务、宏任务两类——微任务是那种执行完立即回调的，宏任务则是通过注册定时器将执行推迟进行，优先级最低。

setInterval 在语义层面友好，但有一个潜在问题：如果回调本身比较耗时，会发生叠加现象。而 setTimeout 是一次性注册，回调完自动清理，可以通过递归方式模拟 setInterval，确保稳定、不会出现叠加。

如何选择需要根据回调本身来决定。存在就有意义，选择是智慧。

## 学习感悟

由 setInterval、setTimeout 一个点，引申出整条知识线：微任务、宏任务的区别，两种定时器各自的能力边界和选型依据，微任务的注册时机（I/O 完成后才入队），再到浏览器多线程模型。

由点到线，由线到面，由面到体。将知识串联、织成网，在实际应用中才能做出更好的选择。
