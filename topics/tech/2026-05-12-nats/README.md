# NATS 基本原理

## 一、NATS 是什么

一个轻量级、高性能的消息通信系统，用于分布式系统中的服务间消息传递。

核心模型极简：

```
发布者(Publisher) → Subject(主题) → 订阅者(Subscriber)
```

Subject 用 `.` 分层，支持通配符：`*` 匹配一层，`>` 匹配多层。

三种通信模式：Pub/Sub（广播）、Request/Reply（请求响应）、Queue Group（竞争消费）。

关键特性：极快（百万级消息/秒）、极轻（单二进制文件，无依赖）、默认 At Most Once（不保证送达，追求速度）。

## 二、横向对比 — 消息框架各有所长

| 框架 | 核心能力 | 定位 |
|---|---|---|
| NATS | 快速广播 | 轻量消息转发 |
| Kafka | 海量持久化 | 大数据流处理 |
| Redis Pub/Sub | 轻量实时推送 | 缓存 + 简单消息 |
| RabbitMQ | 复杂路由 | 企业级消息队列 |

每个框架只解决一个问题，在自己的领域做到极致。

## 三、真实业务场景 — 为什么不能只依赖单一框架

以微博/微信上亿级通知为例，单一框架无法满足：
- 快速广播（NATS 擅长）
- 持久化存储（Kafka 擅长）
- 热数据缓存（Redis 擅长）
- 结构化查询（MySQL 擅长）

实际方案是**推拉结合 + 多层架构**：普通用户推模式，大 V 拉模式，活跃粉丝预计算。这不是某一个框架能解决的，而是多组件协作。

## 四、设计哲学 — Do One Thing Well

没有一个组件是万能的，但组合起来就是完整的系统。

> 单一组件解决单一问题，架构设计解决全局问题。

反面教训：用 MySQL 做消息队列 → IO 瓶颈；用 Redis 做持久存储 → 数据丢失。不是工具不好，是用错了位置。

这背后的原则是 **Unix 哲学**：Do one thing and do it well。

## 五、感悟 — 从技术到生活

框架要把一件事做到极致，才能在复杂的架构中有一席之地。

人也一样。与其什么都会一点，不如问自己：**我能把哪件事做到极致？**

只有把一件事做到极致，才能在生活这个复杂的"业务场景"中不可替代。
