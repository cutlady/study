# JS 定时器与异步模型 — 学习笔记

> 2026-05-13 | 由 setInterval / setTimeout 引申出的完整知识体系

---

## 一、定时器基础

### 1.1 为什么需要定时器

JavaScript 是单线程的，定时器是让代码"延后执行"或"周期执行"的唯一机制。

### 1.2 setTimeout vs setInterval

| | setTimeout | setInterval |
|---|---|---|
| 行为 | 延迟 N ms 后执行**一次** | 每隔 N ms 执行**一次**（直到清除） |
| 返回值 | timer ID（浏览器：正整数；Node：Timeout 对象） | timer ID |
| 清除 | clearTimeout(id) | clearInterval(id) |

### 1.3 内部机制

定时器**不保证精确时间**：

```
调用 setTimeout(fn, 1000)
  → 浏览器/Node 注册一个定时器
  → 1000ms 后把 fn 放入任务队列
  → 等当前调用栈清空后，事件循环取出 fn 执行
```

**fn 不是在 1000ms 时执行，而是在 ≥1000ms 且主线程空闲时执行。**

## 二、核心区别：累积误差

### 2.1 实验对比（300ms 阻塞模拟主线程繁忙）

**setInterval — 误差累积：**

```
tick=1  误差=4ms
tick=2  误差=5ms
tick=3  误差=21ms
tick=4  误差=206ms   ← 累积
tick=5  误差=506ms   ← 继续累积
```

原因：setInterval 按固定节奏往队列塞回调，前一次没执行完，下一次已经在队列等着了。主线程空闲后积压的回调**连续执行**。

**递归 setTimeout — 误差不累积：**

```
tick=1  误差=4ms
tick=2  误差=4ms
tick=3  误差=4ms
tick=4  误差=5ms
tick=5  误差=5ms   ← 始终稳定
```

原因：每次回调执行**完毕后**才开始计算下一个 1000ms。

### 2.2 递归 setTimeout 模式

```js
function repeatedTask() {
  // 做一些事...
  setTimeout(repeatedTask, 1000); // 做完后才注册下一次
}
setTimeout(repeatedTask, 1000);
```

优势：
- 不会累积误差
- 不会出现回调积压
- 可以动态调整下一次间隔

## 三、setInterval 的存在意义

功能上 setTimeout 递归能替代 setInterval，但 setInterval 仍有价值：

| 维度 | 说明 |
|---|---|
| **语义清晰** | `setInterval(fn, 1000)` 直接表达"周期性"，递归 setTimeout 混入了实现细节 |
| **最小延迟限制** | 嵌套超过 5 层的 setTimeout 强制 ≥4ms，setInterval 不受此限 |
| **性能开销** | setInterval 注册一次，递归 setTimeout 每次都要重新注册 |
| **历史原因** | setInterval 更早出现，早期简单场景够用 |

## 四、JS 代码分类：同步 vs 异步

```
JavaScript 代码
├── 同步 — 立即执行，调用栈直接跑（console.log、变量赋值、函数调用）
└── 异步 — 延后执行，交给事件循环调度
      ├── 微任务 — Promise.then/catch/finally、MutationObserver、queueMicrotask
      │         优先级高，本轮同步跑完后立刻清空
      └── 宏任务 — setTimeout/setInterval、I/O 回调、UI 事件、setImmediate(Node)
                优先级低，下一轮事件循环才取
```

**优先级：同步 > 微任务 > 宏任务**

```js
console.log('1');                                // 同步，立即
setTimeout(() => console.log('2'), 0);           // 宏任务
Promise.resolve().then(() => console.log('3'));  // 微任务
console.log('4');                                // 同步，立即

// 输出：1 → 4 → 3 → 2
```

### 事件循环每一轮

```
1. 取一个宏任务执行
2. 清空所有微任务（一个接一个，直到队列空）
3. 渲染（如果需要）
4. 回到 1
```

## 五、网络请求的完整过程

**"微任务优先级高"指的是回调进入队列后的优先级，跟请求本身耗时无关。**

```
时间线：

0ms     fetch(url).then(res => console.log('拿到了'))
        JS 线程：调用 fetch()，注册 .then 回调，不等待，继续跑同步代码

        ===== 浏览器网络线程在后台工作，和 JS 线程无关 =====

5000ms  网络线程：收到响应数据，通知事件循环
        → .then 回调放入微任务队列
        → 当前宏任务结束 → 清空微任务 → 回调执行
```

```
┌─────────────────────────────────────────┐
│  JS 线程（单线程）                        │
│  - 调用 fetch()，注册 .then 回调          │
│  - 继续跑同步代码                         │
│  - I/O 完成后执行 .then 回调              │
└──────────────┬──────────────────────────┘
               │ 发起请求 / 接收结果
┌──────────────▼──────────────────────────┐
│  浏览器底层（多线程）                      │
│  - 网络线程：真正的 HTTP 请求             │
│  - DNS 线程：域名解析                     │
│  - TCP 线程：建立连接                     │
│  ...这些和 JS 线程并行运行               │
└─────────────────────────────────────────┘
```

**JS 单线程 ≠ 整个浏览器单线程。** I/O 交给浏览器其他线程，完成后通过事件循环通知 JS 线程。

### 浏览器的单线程模型会改吗

**不太可能。** 不是技术做不到，而是代价太大。

DOM 操作的多线程问题——线程A在写一个节点，线程B在删同一个节点，谁先谁后？需要加锁，前端开发者就要处理死锁、竞态条件，Web 开发的复杂度会暴涨。整个 Web 生态都建立在"JS 单线程操作 DOM"的假设上，改掉等于推翻一切。

**方向不是改掉单线程，而是把更多工作移出主线程：**

```
浏览器进程
├── JS 主线程（单线程，跑你的代码）
├── 网络线程（HTTP 请求）
├── 渲染线程（布局、绘制）
├── 合成线程（GPU 合成）
├── Worker 线程（你主动创建的）
└── ...
```

JS 已有的多线程能力：

| 技术 | 能力 | 限制 |
|---|---|---|
| Web Worker | 后台线程跑 JS，计算密集型任务 | 不能操作 DOM |
| Service Worker | 代理网络请求，离线缓存 | 不能操作 DOM |
| SharedArrayBuffer | 多线程共享内存 | 不能操作 DOM |
| OffscreenCanvas | Worker 中渲染 Canvas | 仅限 Canvas |

**所有多线程能力都有一个共同限制：不能碰 DOM。** 所以主线程的单线程模型不会变，性能优化的核心目标就是让主线程做越来越少的事。

## 六、微任务的隐患：队列阻塞

微任务是同步清空的，如果微任务里又产生新的微任务，队列会一直涨：

| 微任务数量 | 执行耗时 | 宏任务被延迟 |
|---|---|---|
| 100 | ~0.1ms | 几乎无感 |
| 1,000 | ~0.3ms | 几乎无感 |
| 10,000 | ~4ms | 开始有感知 |
| 100,000 | ~30ms | 明显阻塞，页面卡顿 |

微任务队列不清空，后续的宏任务和渲染都无法执行。

## 七、选型指南

| 场景 | 选择 | 原因 |
|---|---|---|
| 延迟执行一次（toast 消失） | setTimeout | 只需要一次 |
| 简单时钟/倒计时 | setInterval | 语义清晰，短期误差可忽略 |
| 固定节奏轮询 | 递归 setTimeout | 避免请求积压 |
| 回调耗时可能超过间隔 | 递归 setTimeout | setInterval 会积压 |
| 需要动态调整间隔 | 递归 setTimeout | 灵活控制 |
| 动画帧 | requestAnimationFrame | 与屏幕刷新同步 |

---

## 八、费曼总结

JS 是单线程的。有同步代码，有异步代码。其中异步代码又分为微任务、宏任务两类——微任务是那种执行完立即回调的，宏任务则是通过注册定时器将执行推迟进行，优先级最低。

setInterval 在语义层面友好，但有一个潜在问题：如果回调本身比较耗时，会发生叠加现象。而 setTimeout 是一次性注册，回调完自动清理，可以通过递归方式模拟 setInterval，确保稳定、不会出现叠加。

如何选择需要根据回调本身来决定。存在就有意义，选择是智慧。
